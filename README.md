# Mighty Final Fight (U) — дизасемблер для ca65

[English version](README.en.md)

Дизасемблі гри **Mighty Final Fight** (NES, USA, MMC3, 128 КБ PRG + 128 КБ CHR) для асемблера ca65/ld65 та Python-скрипти,
які генерують його з ROM і CDL-файлу (FCEUX). Результат збирається назад **байт-у-байт** в оригінальний ROM.

> ROM, CDL і графіка гри в репозиторій **не входять**. Потрібен власний ROM; графіку (CHR) витягує скрипт.

## Підготовка і збірка

Потрібні: [cc65](https://cc65.github.io/) (`ca65` і `ld65` у `PATH`) та Python 3.8+ (лише стандартна бібліотека).

1. Покладіть свій ROM у корінь репозиторію з іменем `Mighty Final Fight (U) [!].nes`.
   Очікувані контрольні суми (файл з iNES-заголовком, 262160 байт):
   - CRC32 `15EB0BEE`
   - SHA-1 `1bb410bc457694fe3109791b6be8f75bf157b8c8`
2. Витягніть графіку з ROM (створює `src/chr/chr_XX.chr` і PNG-аркуші в `gfx/`):
   ```
   python tools/chr_tool.py split
   ```
3. Зберіть:
   ```
   assemble.bat        # ca65 + ld65 -> mff.nes, mff.map, mff_labels.txt
   compare.bat         # fc /b mff.nes з оригіналом (має збігатися повністю)
   ```
   (або вручну: `ca65 -g src/main.asm -o src/main.o` і
   `ld65 -C config.cfg -Ln mff_labels.txt -m mff.map -o mff.nes src/main.o`)

### Редагування графіки
`gfx/sheet_NN.png` — аркуші по 8 КБ CHR (банки NN\*8 … NN\*8+7 по 1 КБ), 16 тайлів у ряд, 2-бітний індексований PNG.
Після правки в будь-якому редакторі, що зберігає індекси палітри:
```
python tools/chr_tool.py png2chr    # gfx/sheet_XX.png -> src/chr/chr_XX.chr
```

## Перегенерація асемблерних файлів з CDL
Потрібні ROM і власний CDL з FCEUX (`Mighty Final Fight (U) [!].cdl`, тобто той самий каталог):
```
python tools/disasm.py --build      # згенерувати src/, зібрати mff.nes і порівняти з оригіналом
```
Прапори: `--out DIR` (писати в інший каталог), `--labels DIR` (інша тека з `ram.txt`/`rom.txt`), `--no-trace` (без статичного
дотрасування коду), `--no-chr`, `--rom`, `--cdl`. Якщо примусовий діапазон `data`/`table`/`text` перекриває байти, які CDL
бачив як код, генератор друкує `WARNING`.

**Увага:** `disasm.py` перезаписує `src/`. Коли почнете правити `src/*.asm` вручну — не запускайте його в тій самій
теці (генеруйте через `--out` і порівнюйте). Поки asm не правиться руками, імена міток і RAM краще вести у
`tools/labels/*.txt` та перегенеровувати.

## Формат рядка
`LDA ram_0061   ;C - - - - - 0x01E010 0F:E000: A5 61` — прапори CDL (`C` код, `D` дані, номер банку CPU для даних,
`J` непрямий перехід, `I` непрямі дані, `A` PCM), зсув у `.nes`, банк (8 КБ):адреса, байти.
`c` замість `C` — код, знайдений дотрасуванням (емулятор його не бачив; перевірте вручну, список у `docs/coverage.txt`).
`W` — слово таблиці вказівників (`.word`). `- - - - - -` — байти, яких CDL не торкався.

## Що робить генератор
1. Розмічає код/дані за CDL. Інструкції на межі банків ($9FFF→$A000, $DFFF→$E000) та гілки в сусідній банк лишаються
   `.byte` з розшифровкою в коментарі (ca65 не вміє гілки між сегментами).
2. Дотрасовує код: з гілок/`JSR`/`JMP`/провалів у невідомі байти (відкидає шлях при невалідному опкоді, `BRK`,
   наїзді на дані).
3. Знаходить таблиці вказівників (в т.ч. «RTS-трюк», `.word label-1`): якір — слово, що вказує на код з прапором `J`,
   далі розширення в обидва боки, поки слова вказують на код. Елемент «сильний», якщо рівно один банк-кандидат має
   там інструкцію (або рівно один — з прапором `J`), і «слабкий», якщо це невідомі байти, що чисто декодуються як код;
   таблиця приймається лише коли сильних не менше, ніж слабких (інакше таблиця «виростала» в тайлові/спрайтові дані).
   Елементи з неоднозначним банком мають погоджуватися на один банк, інакше виводяться як сирі `$XXXX` без мітки —
   те саме для розділених lo/hi-таблиць (п. 5). Список знайдених таблиць із лічильниками — у `docs/coverage.txt`.
   Цілі таблиць теж трасуються.
4. Ставить мітки `sub_/loc_/ofs_/tbl_/dat_BB_AAAA`. Банк для адрес `$8000–$BFFF` визначається так: (а) єдиний кандидат за CDL;
   (б) пари банків, що завжди підключені разом (00/01, 04/05, 08/09, 0C/0D); (в) лінійне відстеження значень, записаних у
   `prgBank8000/prgBankA000` ($F4/$F5) у фіксованих банках. Такі операнди позначені `bank=NN` у коментарі.
5. Розділені таблиці адрес (lo-байти і hi-байти окремо, `LDA lo,Y` / `LDA hi,Y`) виводяться як `.lobytes`/`.hibytes`,
   пари `LDA #lo / STA zp / LDA #hi / STA zp+1` — як `#<мітка` / `#>мітка`.
6. Невідомі ділянки ≥16 байт, що чисто декодуються і закінчуються `RTS/RTI/JMP`, приймаються як недосяжний код (`c`).
7. Серії однакових байтів (від 8) згортаються в `.res N, $xx`.

## Відомі обмеження
- ~24 КБ PRG (≈19 %) CDL не бачив і трасування не довело до коду — це переважно дані, до яких гра не зверталась під
  час проходження; вони лишаються `.byte` (найбільші ділянки в `docs/coverage.txt`).
- Операнди `$8000–$BFFF`, банк яких залежить від стадії чи набору анімацій (`stageBankTable`), статично не розв'язати; вони мають імена через `rawsym AAAA ім'я` у `rom.txt` (`stagePalettes_s0`, `animPtrLo`…). Один лишився сирим (список у `docs/coverage.txt`).
- Директиви `rom.txt` (у `code|data|words|table|text|bewords|note|comment` замість `BB` можна дати список банків
  `01,05,07:AAAA-AAAA` — та сама CPU-адреса в кожному з них, зручно для банків стадій зі спільною розкладкою):
  `comment BB:AAAA текст` додає коментар у кінець рядка; `bewords BB:LO-HI` виводить пари адрес big-endian (hi, lo) через `>мітка,<мітка`; `text BB:LO-HI` виводить текст рядками з розшифровкою (тайл = ASCII−$31 для A–Z, `$00` пробіл, `$FE` перенос, `$FF` кінець); `table BB:LO-HI N заголовок` виводить діапазон рядками по N байт із коментарем; `bank BB:AAAA TT` вказує банк для сирого операнда `$8000–$BFFF` в інструкції за адресою BB:AAAA.
